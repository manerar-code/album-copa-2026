# ADR-002: Separate Quantities Store Instead of Embedding in UserCollection

## Status

Accepted

## Date

2026-06-16

## Context

Duplicate quantity must be persisted alongside sticker status. Two approaches were considered:
embed quantity directly in `UserCollection` (changing its value type from `StickerStatus` string
to an object), or keep `UserCollection` unchanged and add a parallel
`Record<figurinhaId, number>` store with its own AsyncStorage key.

## Decision

Add a new `quantities: Record<string, number>` slice to `stickerStore` persisted under a
separate AsyncStorage key (`user_quantities_<albumId>`). `UserCollection` and `StickerStatus`
remain unchanged. Stickers absent from `quantities` default to quantity 1 at read time.

## Alternatives Considered

### Alternative B: Embedded in UserCollection

- **Description**: Change `UserCollection` from `Record<string, StickerStatus>` to
  `Record<string, { status: StickerStatus; dupCount: number }>`.
- **Pros**: Single storage key; atomic status+quantity read/write.
- **Cons**: Breaking change — `StickerStatus` string is referenced in dozens of places
  (`toggleSticker`, `setStatus`, `getStatus`, all CromoCard `state=` props, tests). Requires
  runtime migration of every existing stored collection on first load.
- **Why rejected**: Migration risk and blast radius are disproportionate to the feature scope.

## Consequences

### Positive

- Zero change to `UserCollection`, `StickerStatus`, `collectionService`, or any existing
  caller of `toggleSticker` / `setStatus`.
- Backward compatible: existing albums load without migration logic.
- Stickers without a quantities entry default to 1 — no data loss, no UI change.

### Negative

- Two AsyncStorage writes per "increment" tap instead of one.
- Two store slices to load on startup (both are small and load fast).

### Risks

- If `quantities` loads after `collection` on startup, a brief render could show ×1 on all
  cards before quantities arrive. Mitigation: load both in the same `loadCollection` call.
