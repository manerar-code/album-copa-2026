## Context

The Trade Registration modal is triggered exclusively from `DuplicatesScreen`. It needs to live somewhere in the source tree. The project has two natural homes: the `duplicates` module (co-location with the triggering screen) or `shared/components` (for reusable cross-module components).

## Decision

Place `TradeRegistrationModal.tsx` in `src/modules/duplicates/components/`. The modal is not shared — it is owned by the Duplicates feature and has no use case outside it.

## Alternatives Considered

### Alternative B: src/shared/components/

- **Description**: Treat the modal as a shared UI component
- **Pros**: Accessible from other modules in future
- **Cons**: Premature generalization; the modal contains business logic specific to trade registration (parseTradeList, store actions). Shared components should be UI-only.
- **Why rejected**: YAGNI — no other screen uses this modal today; business logic doesn't belong in shared/

### Alternative C: src/modules/trades/components/

- **Description**: Put it in the trades module since it reuses `parseTradeList`
- **Pros**: Logical grouping with parse logic
- **Cons**: Creates a cross-module dependency (duplicates screen importing from trades module); `parseTradeList` is already importable from its util path directly
- **Why rejected**: Cross-module coupling with no benefit

## Consequences

### Positive

- Clear ownership: Duplicates feature owns its modal
- No cross-module coupling
- Consistent with how other modules own their components (e.g., `auth/components/ProfileModal`)

### Negative

- `parseTradeList` is imported from `trades/utils/` into a `duplicates/` component — this is a cross-module utility import, which is acceptable (utils are designed for reuse)
