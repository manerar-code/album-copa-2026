## Context

The Trade Registration feature must process two lists of sticker IDs simultaneously: sent stickers (decrement or promote to owned) and received stickers (set to owned). The stickerStore already has individual actions (`setStatus`, `incrementDupCount`, `resetSticker`) that each perform one AsyncStorage write and one cloud sync call per sticker.

## Decision

Add a single `registerTrade(sent: string[], received: string[])` action to `stickerStore`. The action applies all mutations in memory first, then performs ONE `collectionService.save` and ONE `quantitiesService.save`, followed by `Promise.all` for cloud sync of only the changed stickers.

## Alternatives Considered

### Alternative B: Loop over existing actions

- **Description**: Call `setStatus()` in a loop for each sticker ID
- **Pros**: Reuses tested code, zero new action surface
- **Cons**: Generates N sequential AsyncStorage writes and N sequential cloud calls; partial failure leaves collection in inconsistent state mid-trade
- **Why rejected**: Performance and consistency — a 10-sticker trade would trigger 10+ separate persists

### Alternative C: Fire-and-forget sequential loop

- **Description**: Non-blocking loop calling `setStatus` without awaiting each
- **Pros**: Simplest code
- **Cons**: Race conditions on AsyncStorage, no way to revert on failure
- **Why rejected**: Reliability risk

## Consequences

### Positive

- Single AsyncStorage write per trade — atomic from user perspective
- Simpler rollback: snapshot before mutation, revert entire state on save failure
- Cloud sync parallelized via `Promise.all`

### Negative

- New action surface to maintain in the store
- Must handle the "partial cloud sync failure" case (some upserts succeed, some don't)

### Risks

- Cloud partial failure: if one `upsertOne` throws, others already resolved. Mitigation: cloud sync failures are non-reverting (data is safe in AsyncStorage); log the failure and let next app open re-sync.
