# ADR-002: Dedicated Table for Account Deletion State

## Status

Accepted

## Date

2026-06-10

## Context

F5 (Account Deletion with Grace Period) requires persisting a "pending deletion" state per
user account, including the request timestamp, the scheduled deletion timestamp (request +
30 days), and an optional cancellation timestamp. This state must survive between app
sessions, be queryable by server-side jobs, and be protected by Row-Level Security.

Three candidate locations were evaluated: a dedicated table, an existing table column, and
Supabase Auth `user_metadata`.

## Decision

Create a new `account_deletion_requests` table in Supabase with columns:
- `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`
- `user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE`
- `requested_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `scheduled_delete_at TIMESTAMPTZ NOT NULL` (= requested_at + 30 days)
- `cancelled_at TIMESTAMPTZ` (nullable — set when user cancels)
- `completed_at TIMESTAMPTZ` (nullable — set after permanent deletion)

RLS: `user_id = auth.uid()` for SELECT/INSERT/UPDATE. The scheduled cleanup job runs with
the Supabase `service_role` key (bypasses RLS).

## Alternatives Considered

### Alternative B: Column on `user_albums`

- **Description**: Add `pending_deletion_at TIMESTAMPTZ` to the existing `user_albums` table
- **Pros**: No new migration required beyond an ALTER TABLE; simpler schema surface
- **Cons**: Mixes account lifecycle concerns with collection data; breaks single-responsibility;
  if user has multiple albums, which row carries the deletion state?
- **Why rejected**: Structural mismatch — `user_albums` is scoped per album, not per user account

### Alternative C: `auth.users.raw_user_meta_data`

- **Description**: Store deletion state as JSON in `supabase.auth.updateUser({ data: { pendingDeletionAt: '...' } })`
- **Pros**: No migration, no new table, zero schema change
- **Cons**: `user_metadata` is not protected by table-level RLS policies; no server-side
  queryability without elevated privileges; no `scheduled_delete_at` column for Supabase
  scheduled jobs to filter on; harder to audit for LGPD compliance
- **Why rejected**: Non-auditable, not queryable by edge functions without service_role overhead

## Consequences

### Positive

- Clean separation of account lifecycle from collection data
- `scheduled_delete_at` column enables a simple WHERE clause in the cleanup Edge Function
- RLS policies are straightforward and isolated from existing table policies
- `ON DELETE CASCADE` ensures the record is cleaned up if auth.users row is deleted directly
- LGPD audit trail: `requested_at`, `cancelled_at`, `completed_at` timestamps are available

### Negative

- One additional table migration required
- RLS policy must be written and tested for the new table

### Risks

- **Orphaned records**: If `user_collections`/`user_albums` deletion fails partway through,
  the account exists but data is partially removed. Mitigation: run deletions inside a
  Postgres transaction in the Edge Function, catch errors and mark `completed_at` only on
  full success.

## Implementation Notes

```sql
CREATE TABLE account_deletion_requests (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  requested_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  scheduled_delete_at TIMESTAMPTZ NOT NULL,
  cancelled_at TIMESTAMPTZ,
  completed_at TIMESTAMPTZ
);

ALTER TABLE account_deletion_requests ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users manage own deletion request"
  ON account_deletion_requests
  FOR ALL
  USING (user_id = auth.uid())
  WITH CHECK (user_id = auth.uid());
```
