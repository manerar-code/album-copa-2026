# ADR-001: Phased Sequential Implementation for Store Launch Readiness

## Status

Accepted

## Date

2026-06-10

## Context

The technical audit of Álbum Copa 2026 identified 14 items spanning four distinct concerns:
security & credentials, LGPD/compliance, store readiness, and code quality/refactoring.
All items must be resolved before publishing to the Apple App Store and Google Play Store.
The app targets Brazilian users only, so LGPD compliance is mandatory. The development is
primarily done by a solo developer, making parallel tracks risky.

## Decision

Implement all 14 audit items in four sequential phases:
- **Phase 1 — Infrastructure & Security**: Credentials, RLS, dependency updates, build config
- **Phase 2 — Compliance & Privacy**: Privacy policy screen, account deletion with 30-day
  grace period, login error feedback
- **Phase 3 — Store Readiness**: iOS Privacy Manifest, asset validation, full store metadata
- **Phase 4 — Code Quality**: React.memo, ProfileModal extraction, CatalogProvider refactor,
  test migration

## Alternatives Considered

### Alternative B: Two Parallel Tracks

- **Description**: Technical track (security + refactoring) runs in parallel with product track
  (compliance + store metadata)
- **Pros**: Faster overall timeline (~2 weeks vs ~4 weeks)
- **Cons**: Merge conflicts risk, requires coordination, harder for solo developer
- **Why rejected**: Solo development context makes parallel tracks risky and inefficient

### Alternative C: Minimum Compliance for Submission

- **Description**: Implement only the minimum required items for store submission, defer
  code quality items to post-launch patch releases
- **Pros**: Fastest time to market
- **Cons**: Technical debt ships to production; risk of Apple/Google review rejection
  if reviewers identify missing compliance items; LGPD exposure
- **Why rejected**: Risk of app rejection is too high; LGPD non-compliance in Brazil
  carries fines; user trust is eroded by visible technical debt

## Consequences

### Positive

- Each phase is independently deployable and testable
- Clear dependency chain: Phase 2 requires Phase 1 (RLS must be live before account deletion)
- Lower merge conflict risk with sequential implementation
- Each phase delivers a verifiable milestone before proceeding

### Negative

- Longer total timeline (~3–4 weeks) compared to parallel approach
- Store submission blocked until all four phases are complete

### Risks

- **LGPD deadline risk**: If Apple/Google reject submission due to missing Privacy Policy URL,
  the in-app screen alone does not satisfy their requirements — mitigation: also publish
  a public URL on Vercel (noted in PRD Open Questions)
- **Phase 4 scope creep**: Refactoring can expand; mitigation: each item is strictly
  scoped to the audit finding, no new features
