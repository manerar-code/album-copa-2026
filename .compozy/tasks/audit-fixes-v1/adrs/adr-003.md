# ADR-003: Sign in with Apple via expo-apple-authentication + signInWithIdToken

## Status

Accepted

## Date

2026-06-08

## Context

App Store Guideline 4.8 requires Sign in with Apple whenever an app offers any third-party social login. The app currently provides Google OAuth via `expo-web-browser` and Supabase OAuth redirect. Sign in with Apple must be added before App Store submission.

## Decision

Use `expo-apple-authentication` to obtain an Apple identity token natively, then call `supabase.auth.signInWithIdToken({ provider: 'apple', token })` to authenticate with the existing Supabase project. This reuses the existing auth flow in `authService.ts` without new screens or redirect URLs.

Implementation:
1. `npx expo install expo-apple-authentication`
2. Add `expo-apple-authentication` to `app.json` plugins.
3. In Supabase Dashboard → Auth → Providers, enable Apple and configure Service ID + key.
4. Add `signInWithApple()` method to `authService.ts` using `AppleAuthentication.signInAsync()`.
5. Add Apple button to the existing login UI (rendered only on iOS via `AppleAuthentication.isAvailableAsync()`).

## Alternatives Considered

### Alternative: OAuth redirect via expo-web-browser (same as Google)
- **Description**: Use Supabase's OAuth redirect flow with `expo-web-browser`, same pattern as Google login.
- **Pros**: Consistent implementation pattern with existing Google flow.
- **Cons**: Requires custom URL scheme callback configured in Apple Developer Portal. Apple's OAuth redirect flow on iOS opens a Safari modal, which is a worse UX than the native Sign in with Apple sheet. Also requires `openAuthSessionAsync` which has known iOS timing issues.
- **Why rejected**: Native `signInAsync` provides better UX and is simpler to configure.

### Alternative: Defer until after first App Store submission
- **Description**: Submit without Sign in with Apple, address rejection if Apple enforces it.
- **Pros**: No additional development work before first submission.
- **Cons**: App Store Review Guideline 4.8 is enforced for apps with social login. Rejection adds 1–2 weeks delay. Risk is not worth it.
- **Why rejected**: High probability of rejection; faster to implement correctly.

## Consequences

### Positive
- Complies with App Store Guideline 4.8 — no rejection on this grounds.
- Native Sign in with Apple sheet provides best UX on iOS (FaceID/TouchID integration).
- Reuses existing auth store and user session management.

### Negative
- Requires Apple Developer Portal configuration (Service ID, private key) — manual step.
- Sign in with Apple button only appears on iOS (correct per Apple guidelines — not required on Android).
- Supabase Apple provider requires additional setup in the dashboard.

### Risks
- Apple Developer Portal approval for new capability can take 1–3 days.
- Mitigation: configure the Apple Developer Portal Sign in with Apple capability immediately at Phase 2 start.
