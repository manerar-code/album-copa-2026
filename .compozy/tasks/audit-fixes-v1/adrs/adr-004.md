# ADR-004: cloudCollectionService.replaceAll — Check Insert Error and Throw

## Status

Accepted

## Date

2026-06-08

## Context

`replaceAll` in `cloudCollectionService.ts` deletes all rows for a `user_album_id`, then inserts new rows. The insert result is currently discarded — if it fails, the collection is silently left empty in the cloud. This can cause permanent data loss for users who sync after a transient network error.

## Decision

Destructure and check the error from the Supabase insert call. If `error` is non-null, throw it so the caller's `catch` block handles it:

```typescript
if (rows.length > 0) {
  const { error } = await supabase.from('user_collections').insert(rows);
  if (error) throw error;
}
```

The existing outer `try/catch` in `replaceAll` already calls `handleError(error, ...)` and re-throws, so callers will receive the error and can display an appropriate message.

## Alternatives Considered

### Alternative: Upsert (replace delete+insert with upsert)
- **Description**: Use `supabase.from('user_collections').upsert(rows, { onConflict: 'user_album_id,figurinha_id' })` to eliminate the empty intermediate state.
- **Pros**: Atomic — no window where collection is empty. Naturally idempotent.
- **Cons**: Requires a unique constraint on `(user_album_id, figurinha_id)` at the database level. Cannot remove rows that are now 'missing' without a separate delete step. Schema change required.
- **Why rejected**: Requires database schema change (unique constraint). The delete+insert pattern already handles 'missing' removal correctly; fixing error propagation is sufficient.

### Alternative: Transaction via Supabase RPC
- **Description**: Create a PostgreSQL stored procedure that wraps delete + insert in a transaction.
- **Pros**: True atomicity at the database level.
- **Cons**: Requires database migration and RPC function creation. Overkill for the current failure mode (network errors, not concurrent writes).
- **Why rejected**: Over-engineered for the problem. Error propagation fix is sufficient.

## Consequences

### Positive
- Data loss from silent insert failure is eliminated.
- Existing error handling chain (`handleError`) is reused without changes.
- Minimal code change: one destructured assignment and one `if` check.

### Negative
- A delete + failed insert still leaves the collection empty until the next successful sync.
- Mitigation: callers should catch the error and retry or inform the user.
